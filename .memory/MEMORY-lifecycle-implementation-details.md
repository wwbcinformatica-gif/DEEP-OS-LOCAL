## Lifecycle implementation details

- **LifecycleConfig already has `max_think_only_loops=3`** — user wants separate limits: 5 THINK_ONLY + 7 tool calls per subtask. These are independent counters. (Now implemented via CircuitBreaker.)
- **`truncate_messages()` in llm_native.py is crude** — drops middle messages, keeps system + last N + last user. Now supplemented by `compress_context()` in lifecycle.py which does semantic compression of old blocks.
- **Brain learning hooks into vectorstore**: `aprender_com_a_tarefa()` in `brain.py` appends to faq.json then calls `rebuild_vectorstore()`. Extended with secondary elastic memory indexing.
- **`get_rag_context()` exists but NOT used in agent loop START** — only used in `handle_question_stream()`. Gap closed by `recall_relevant_memories()` in `elastic_memory.py` which is called at START in `agents/loop.py`.
- **Elastic memory cosine threshold tuned to 0.15**: Lower than typical 0.3 because task descriptions are short. May need retuning as index grows.
- **Context compression uses 75% trigger ratio**: Conservative to avoid over-compression. Reactive window (reopens every 5 steps) prevents repeated compression on same content.
- **StateHashTracker uses MD5**: Short enough for performance, long enough for meaningful differentiation of reasoning+tool patterns.
- **Atomic write for Windows JSON files**: `tempfile.mkstemp()` + `os.replace()` with fallback to `unlink()` + `rename()` when `os.replace()` fails. Required for safe concurrent writes to `index.json`.
- **Contextualized nudges > generic nudges**: Models ignore generic "stop looping" messages. Nudges with last 5 tool actions + errors + forced self-explanation + explicit strategy-change options (A-D) produce measurably better recovery.
- **Failure lessons as anti-pattern training data**: Indexing failures with `[FAILURE_LESSON]` tag allows future recall to inject warnings. `is_failure` flag distinguishes from success entries. Same index.json, same cosine search.
- **Graceful failure UX**: Instead of raw "Circuit breaker tripped: Tool calls exceeded (7/7)", users see "I couldn't complete the task after 8 iterations. Tools used: bash, read. Errors: ... Suggestions: 1. Verify permissions..."
- **CircuitBreaker hardcoded limit NOT wired to config.yaml**: `config.yaml:agent.max_tool_steps=100` exists but CircuitBreaker defaults are hardcoded to 7 in three locations: `core/state_machine.py:148` (class default), `core/lifecycle.py:141` (LifecycleConfig dataclass default), `agents/loop.py:99` (instantiation). This causes the agent to disarm at 7/7 tool calls despite the UI showing 100. Fix requires raising defaults and/or wiring to config.yaml.
- **Checklist event wiring bug root cause (2026-06-21)**: `on_tool_end_fn` (chat.py:727-730) updates `checklist_steps[checklist_active]["status"] = "done"` but does NOT append to `state_ref["yielded"]` (unlike `on_tool_start_fn` which does at line 725). The yielded events are only flushed at lines 831-833 (after tool_start) and 860-862 (after tool_end) — but the tool_end flush happens AFTER `on_tool_end_fn` runs, so the "done" status IS included. The real issue: `task_progress` parsing only runs inside `thinking` events (chat.py:788). Lifecycle engine's `_handle_tool_calls()` yields `tool_start` → `tool_end` → `thinking` events. The `thinking` event at lifecycle.py:811 contains `[APPEND_OBSERVATION]` text, NOT the model's accumulated content with `task_progress` JSON. So the regex at chat.py:802 never matches — the `task_progress` JSON is in `accumulated_content` but that's never yielded as a `thinking` event during tool execution.
- **Custom prompt bypass for checklist (2026-06-21)**: `build_system_prompt()` in `chat.py:365-394` uses `msg.system_prompt` directly when provided (line 366), bypassing `TOOL_SYSTEM_PROMPT.format()` which includes `TASK_CHECKLIST_PROMPT`. When `is_greeting` is True, the personality instruction is returned alone. Fix: always append `TASK_CHECKLIST_PROMPT` after any prompt content (personality or custom).
- **checklist_active init bug (2026-06-21)**: In `chat.py`, `checklist_active` initialized to `-1` but `on_tool_start_fn` auto-advance checks `checklist_active >= 0`. When model sent no `task_progress` events, auto-advance was dead code. Fixed by setting `checklist_active = 0` on `task_plan` receipt. Pattern: closures reading outer-scope variables that are only conditionally updated — verify init values match all code paths.
- **Lifecycle iteration-break architecture (2026-06-21, IMPLEMENTING)**: The "model cheating" problem — model sends task_plan + tool_calls in single API response, lifecycle executes both in one pass, all checkboxes appear `[x]` instantly. **Root cause**: `run_lifecycle()` TOOL_CALLS branch (lifecycle.py:378-422) calls `_handle_tool_calls()` in same iteration after `has_presented_plan = True`. **Fix**: When plan is detected for first time, yield plan event and `continue` loop WITHOUT executing tools — model must re-call in next iteration to actually execute. Two checklist systems coexist: backend `task_checklist` events (from `task_plan` JSON parsing in chat.py:763-773) AND frontend markdown checkbox parsing from streaming text.
- **Last checkbox stuck bug + fix (2026-06-21)**: Stream closes before the final `task_checklist done` event arrives, leaving the last step in `[~] EM ANDAMENTO` state with counter at `3/4`. Fix: when `loading` transitions `true→false` (agent finished), force-override all checklist steps to `done` in `TaskChecklist.tsx` or upstream state. The component is stateless (pure `steps` prop) — fix lives either as a `completedOverride` prop on TaskChecklist, or as a `useEffect` in App.tsx/ChatPanel that mutates steps when loading ends. Counter `{completed}/{total} ({pct}%)` auto-corrects to `4/4 (100%)` once all steps are `done`. The "EM ANDAMENTO" badge naturally hides since `running = steps.find(s => s.status === 'running')` returns undefined.
