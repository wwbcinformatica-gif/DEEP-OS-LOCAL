## Media Player & AI Actions

- **Mini MusicPlayer in top bar (2026-07-02, IMPLEMENTED)**: Inline audio+video player component placed in top navigation bar. "+" button for file upload, prev/play/next controls, progress seek bar, volume slider, track list dropdown. Uses `URL.createObjectURL()` per file, auto-advance on track end. Now supports video (mp4, wmv, avi, mkv, webm, mov) with mini widescreen preview (4 sizes: XS/SM/MD/LG). Component at `MusicPlayer.tsx`, uses `forwardRef` + `useImperativeHandle` for AI control.
- **AI Action System — SSE event bridge (2026-07-02, IMPLEMENTED)**: Backend emits `{ type: 'action', action: 'command_name', payload: {...} }` events in the streaming response. Frontend processes these and executes corresponding UI operations. Commands: `media_play`, `media_pause`, `media_next`, `media_prev`, `media_stop`, `media_list`, `explorer_cd`, `open_file`, `run_terminal`. MusicPlayer exposed via `forwardRef` with imperative methods (`playFile`, `playPause`, `next`, `prev`, `stop`, `getTracks`, `addByUrl`, `setVolume`). This is the core mechanism for AI to control UI for accessibility — natural language → action events → UI execution.
- **Backend system prompt teaches AI action commands (2026-07-02, IMPLEMENTED)**: `TOOL_SYSTEM_PROMPT` in `prompts.py` includes 9 action commands with JSON examples (escaped braces `{{` `}}` for Python `.format()`). Backend `chat.py` parses action events from model's accumulated content via regex, validates against whitelist, forwards to frontend. User's workflow: natural language → AI uses tools (glob, read) to find files → generates action JSON → backend parses → frontend executes.
- **Media API for built-in player (2026-07-02, IMPLEMENTED)**: Backend `routes/media.py` serves local audio/video files via HTTP (`/api/media/search`, `/api/media/file`, `/api/media/scan`). Frontend `App.tsx` handles `media_search` action: fetches from API, loads file via `addByUrl()`, auto-plays in built-in mini player. Security: `ALLOWED_ROOTS` restricts served directories. This enables AI to play media within the DEEP-OS UI instead of opening system players — critical for accessibility (no window switching).
- **Built-in player over system player (2026-07-02, DECIDED)**: User observed that opening Windows Media Player via bash breaks accessibility (window switching). Backend media API serves files for built-in mini player — keeping everything in-app. Pattern: AI uses tools to find files → generates `media_search` action → backend serves via `/api/media/file` → frontend loads in MusicPlayer.
- **Built-in player only — never system player (2026-07-02, DECIDED)**: Model must use `media_search` action instead of bash `start` command to open media files. User said "eu quero que ele abra no media mini ele abre no grande". **Updated**: Now supports player choice via `payload.player` parameter — `'windows'` for system player, `'mini'` for built-in.
- **Tool execution text must be gray (2026-07-06, DECIDED)**: User rejected orange/red for `> bash(...)` stream display. Changed to `var(--muted)`. User finds prominent colors distracting for execution output.

## Voice & Speech

- **Voice wake words for hands-free control (2026-07-02, IMPLEMENTED)**: VoiceAssistant.tsx component uses Web Speech API with `continuous=true` for wake word detection. Commands: "ok mic" (activate microphone), "ok voz" (activate speaker/TTS), "ok jarvis" (both). Also supports "desativa mic/voz/jarvis", "pare/silencio", "ajuda". Button "VOZ" in ChatPanel next to microphone icon. Critical for accessibility — users who cannot use hands can control everything by voice.
- **Word-boundary matching for voice commands (2026-07-02, IMPLEMENTED)**: Replaced substring matching (`includes()`) with regex word boundaries `(^|\s)word(\s|$)` via `hasWord()`. Multi-word phrases use ordered word-by-word matching via `hasPhrase()`. STOP command ("pare"/"silencio") requires standalone word; "para" only matches in phrases ≤3 words to prevent false triggers in "abra o arquivo para mim". Critical fix — false triggers made the system unusable for real commands.
- **No auto-speak — voice on demand (2026-07-02, DECIDED)**: User explicitly said responses should not be read aloud automatically. Model executes silently; only reads when user says "ler tudo". This is an accessibility decision — auto-speak was slow and distracting for the user. **Exception**: Execution plans ("PLANO DE EXECUCAO") should be spoken aloud for accessibility.
- **Continuous listening during idle (2026-07-02, DECIDED)**: User requires microphone to stay active during model idle state. "na tela de ocioso ele tem que ficar ativo q me escutar para que eu fale continue". The `onend` handler always restarts recognition without conditional checks.
- **Voice confirmation over click confirmation (2026-07-02, DECIDED)**: For accessibility, plan approval and tool confirmation must work by voice ("sim, pode fazer") in addition to click buttons. Critical for users who cannot use mouse/keyboard.
- **Refs-based recognition stability (2026-07-02, DECIDED)**: Speech recognition callbacks must read from refs, not state, to avoid stale closures and infinite recreation loops. All values accessed inside `onresult`/`onerror`/`onend` go through refs.
- **5-second debounce before sending voice (2026-07-02, DECIDED)**: User requires a 5-second debounce window before sending voice to the model. This allows the user to correct misheard speech. Accumulate text, show countdown, send after silence. User can say "confirma" to send early or "cancela" to discard.
- **Keep-alive interval for continuous listening (2026-07-02, DECIDED)**: `setInterval` every 1.5s checking `!wakeRecognitionRef.current` is the PRIMARY mechanism for keeping mic alive. `utterance.onend` and `recognition.onend` are secondary — Chrome doesn't always fire them.
- **Voice speed from slider (2026-07-02, DECIDED)**: TTS rate must use the settings slider. Mapping: `rate = 0.5 + (sliderValue / 100) * 1.5`. Same pattern for pitch. User said "a barra de velocidade tem que alterar a velocidade da voz dele".
- **Text accumulation pattern for voice (2026-07-02, DECIDED)**: Web Speech API `isFinal` results fire incrementally. Must accumulate all text until `onend` fires, then process complete sentence. Processing each `isFinal` individually causes phrases to be cut short (user speaks full sentence but only first few words captured).
- **Inline voice status display (2026-07-02, DECIDED)**: Voice status shown as inline `<span>` next to VOZ button, not absolute-positioned tooltip. Shows: debouncing text + countdown, interim transcription, confidence %, or "ouvindo...". Tooltip caused layout issues.
- **Echo cancellation approach: stop/restart recognition (2026-07-06, COMPLETED)**: Three options evaluated: (1) getUserMedia + custom pipeline — complex, breaks browser STT, (2) AudioContext analyser — needs mic stream, (3) Stop/restart recognition around TTS — simplest, reliable. Chose option 3. `isSpeakingRef` coordinates TTS and STT. 1000ms delay before restart ensures audio has fully stopped. Consistent with existing `autoSendVoiceRef` pattern (refs not state in recognition callbacks).
- **Jarvis speech summary extraction (2026-07-06, COMPLETED)**: Full model responses include code blocks, lists, verbose explanations — not useful for spoken output. `summarizeForSpeech()` strips code blocks, removes list items, takes first 3 meaningful sentences + ellipsis. Applied inside `speakText()` before TTS.
- **Jarvis reads summary only (2026-07-06, COMPLETED)**: User said "o jarvis tem que ler somente o resumo a resposta não ler o contexto todo". Added `summarizeForSpeech()` function: strips code blocks, removes list lines, splits sentences, takes first 3 + ellipsis. Wired into speakText() to replace full response text.
- **Auto-speak only on final done event (2026-07-06, COMPLETED)**: `tool_end` in App.tsx was calling `setStream('')`, triggering auto-speak after each tool execution. Removed `setStream('')` from `tool_end` — stream only clears on final `done` event. Added `lastSpokenMsgRef` dedup guard + 3s cooldown to prevent repeated speech.
- **Speech recognition continuous+interim for full capture (2026-07-06, COMPLETED)**: Changed from `continuous = false, interimResults = false` to `true, true`. Handler accumulates ALL `event.results` entries instead of only `event.results[0][0].transcript`. Only stops listening when ALL results are `isFinal`. Previous config caused long sentences to be truncated.
- **Echo cancellation via isSpeakingRef (2026-07-06, IN PROGRESS)**: When auto mode + Jarvis voice active, SpeechRecognition picks up TTS audio causing infinite feedback loop. Solution: `isSpeakingRef = useRef(false)` coordinated between TTS and STT. Set true before TTS starts, false in audio.onended/utterance.onend. STT auto-restart checks this ref with double-guard (before setTimeout + inside callback). Web Speech API has no getUserMedia control — cannot apply echoCancellation constraints directly. Must stop/restart recognition around TTS playback.
- **llmrtc over echoOLlama for voice (2026-07-02, DECIDED)**: User shared both repos asking "sera que isso ajudaria". llmrtc chosen: (1) TypeScript matches DEEP-OS frontend stack, (2) WebRTC provides lower latency than WebSocket, (3) Built-in VAD solves mic-hearing-TTS feedback loop more elegantly than abort/restart, (4) Barge-in allows interrupting AI mid-speech, (5) Multi-provider support (OpenAI, Anthropic, Ollama, faster_whisper, Piper TTS). echoOLlama is Python/FastAPI (matches backend) but less feature-rich.
- **echoOLlama/llmrtc evaluation (2026-07-02, COMPLETED)**: User shared two repos. echoOLlama: Python/FastAPI + Ollama + faster_whisper + OpenedAI TTS (WebSocket). llmrtc: TypeScript SDK + WebRTC + multi-provider + VAD + tool calling + playbooks. llmrtc chosen for integration — created voice server on port 8787.
- **llmrtc voice-task-assistant works out of box (2026-07-02)**: Fresh clone at `C:\DEEP-OS\llmrtc-main` includes `examples/voice-task-assistant/` with correct push-to-talk implementation using `audioTrack.enabled`. Server uses OpenAI (LLM+STT) + ElevenLabs (TTS) on port 8787. Client at port 5173. Just configure `.env` with API keys and run `npm run dev`.
- **`summarizeForSpeech()` strips tables (2026-07-06, IMPLEMENTED)**: Added regex to remove `|...|` lines before speech extraction. Jarvis reads clean summary without table data.

## Other Implemented Features

- **Conversational model behavior (2026-07-02, DECIDED)**: After completing a task, model should ask "O que voce quer fazer?" and wait for next command. User said "quando eu passar a tarefa para ele ele tem que falar que ja esta pronto e perguntar o que eu quero fazer".
- **DEEP-OS chat requires saved API key (2026-07-02)**: `send()` in `App.tsx:637` validates provider-specific API key before sending. For mimo provider, checks `mimoApiKey` state. If empty in localStorage, shows warning and blocks send. User must enter key in Config page and click "Salvar configuracoes".
- **Voice auto-send pattern (2026-07-03)**: SpeechRecognition.onresult → setInput(transcript) → setTimeout(() => handleSend(transcript), 100). The 100ms delay ensures React state updates before send() reads it. Both onresult handlers in ChatPanel.tsx (lines 237-241 and 274-278) use this pattern.
- **mimo provider: backend owns the API key (2026-07-03)**: Frontend sends empty api_key for mimo; backend reads `MIMO_API_KEY` from `backend/.env`. Frontend validation skips mimo/ollama (no key needed). This centralizes key management.
- **mimo API model constraint (2026-07-03)**: xiaomimimo.com API only accepts `mimo-v2.5` as model name. Sending `deepseek-v4-flash` returns 400. Backend must map provider `mimo` to model `mimo-v2.5`.
- **START-TOTAL.bat simplified (2026-07-03)**: Runs only DEEP-OS (backend 8001, frontend 5175). llmrtc voice-task-assistant removed — requires ElevenLabs paid API key. STOP-TOTAL.bat simplified: kills all node/python processes + cleans ports 8001/5175/8787/5173. No window title filters (unreliable on Windows).
- **Windows taskkill unreliability (2026-07-03)**: `taskkill /F /FI "WINDOWTITLE eq *pattern*"` fails to match on Windows. Use `taskkill /F /IM process.exe` + `netstat -aon | findstr :PORT` for reliable cleanup.
- **File content in chat vs center panel (2026-07-03, DECIDED)**: User asked AI to "abra o arquivo erro 400 aqui no painel do Meio" — AI displayed content in chat instead. User was fine with it ("ta otimo") but noted the expectation. Future: consider routing file content to center panel based on user intent ("abra no meio" / "abra no editor").
- **Voice auto-send toggle (2026-07-03, PARTIAL)**: Added `autoSendVoice` state + `voiceSendTimerRef` to ChatPanel. Timer fires `handleSend(transcript)` after 1.5s delay when enabled. Toggle UI and cancel button not yet added. Second `onresult` handler (~line 274) not yet updated.
- **4-panel vertical layout (2026-07-06, REQUESTED)**: User requested execution processes panel to the right of chat. Layout: Explorer | Editor | Chat | Execution Panel (right). Execution panel will show thinking, tool calls, steps, and other model process information. Not yet implemented.
