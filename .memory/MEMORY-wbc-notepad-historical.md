## WBC NotePad (separate project)

- **WBC NotePad uses Supabase (not Prisma/Firebird)**: 5 tables: `profiles`, `passwords`, `notes`, `user_settings`, `subscription_plans`. All with RLS. Client access via `src/lib/supabase.ts`, server via `src/lib/supabase-server.ts`, admin via `src/lib/supabase-admin.ts`.
- **Trial config stored in notes table**: `app-config.ts` stores trial_days as JSON in a special `notes` row (title="⚙️ Config Globais"). Admin panel reads/writes via `getAppConfig()`/`saveAppConfig()`.
- **handle_new_user() trigger hardcodes 7-day trial**: Supabase trigger does `NOW() + INTERVAL '7 days'` — does NOT read trial_days from notes table. Admin panel trial config does NOT affect new signups. Likely a bug/incomplete feature.
- **Trial config client-side fix applied (2026-07-11)**: `register/page.tsx` and `admin/page.tsx` now use `trialDays` variable instead of hardcoded 7. Three trial paths: (1) admin panel → saveAppConfig → notes table ✅, (2) public register → getAppConfig → uses trialDays ✅, (3) handle_new_user() trigger → still hardcodes 7 days ❌. Client-side profile insert may conflict with trigger.
- **Credit card eye shows front+back side by side (2026-07-11)**: `category/page.tsx` rewritten. When eye clicked, shows both front (full number, holder, validity) and back (magnetic strip, signature lines, CVV) in flex layout. When hidden, normal card with masked number.
- **Input component supports rightElement prop**: `src/components/ui/input.tsx` has `rightElement` prop for rendering icons/buttons inside input field on right side. Available for eye/copy buttons on password fields in edit/new forms.
- **site-app has 4 fields, slice(0,3) hid password**: `catConfig.fields.slice(0,3)` cut off the 4th field (password) for site-app category. Removed slice to show all fields.
- **Bank account mini card has no eye/copy**: `BankAccountCard` variant="mini" (category list) only shows bank name, agency/account, PIX — no password field. Full variant has eye+copy for password.
- **DocumentCard uses dynamic gradient colors**: `DOC_COLORS` map stores `{from, to}` gradient pairs for 10 soft color themes. `getDocColors(colorKey)` returns the pair. Applied via inline `style={{ background: \`linear-gradient(135deg, ${colors.from}, ${colors.to})\` }}`. Each card sub-component (CNH, RG, CPF) accepts `colors` prop.
- **formatDateBR helper for Brazilian dates**: Converts ISO YYYY-MM-DD → DD/MM/YYYY, passes through already-formatted DD/MM/YYYY strings, returns "--" for empty values. Used across all document card date fields.
- **Document colors stored in `doc_color` field**: The `fields.doc_color` string (e.g., "azul-claro") stored in passwords table. Used to look up gradient colors at render time via DOC_COLORS map.
- **Document card header banner convention (2026-07-11)**: Headers must spell out the full document name from abbreviation: RG → "Registro Geral", CNH → "Carteira Nacional de Habilitação", CPF → "Cadastro de Pessoa Física" (singular). Banner background uses the card's gradient `colors.to` color (NOT hardcoded). A divider line separates banner from card body.
- **Document card action button layout (2026-07-11)**: Buttons positioned at `bottom-2 right-4` with `flex items-end gap-2`. Each button wrapped in a `flex flex-col items-center gap-0.5` container with a tiny label (`text-[10px] text-white/50`) above it. Labels in lowercase: "mostrar"/"ocultar" for eye, "cpf", "rg", "cnh" for copy. Applied to front and back of all card types (CNH, RG, CPF).
- **Shopping list inline edit mode styling (2026-07-11)**: `checklist/page.tsx` — inline title input has "Editando" badge (tiny `bg-[var(--theme-primary)]` label), 2px themed border, `bg-[var(--theme-primary)]/5` tint, inner shadow. Non-editing title has hover effect: `hover:bg-[var(--theme-primary)]/5 hover:px-2 hover:-mx-2 hover:py-1 rounded-lg` to signal clickability.
- **Agenda data stored as JSON in notes content field**: Agenda data (date, time, endTime, allDay, reminder, location, status, notes) is stored as JSON string in the `content` field of the `notes` table with `type="agenda"`.

## Historical DEEP-OS discoveries (stable, not current)

- **Web Speech API blocks echoCancellation**: SpeechRecognition manages mic internally via `getUserMedia()` — the app never calls it directly. Cannot apply `echoCancellation: true` constraints. To prevent feedback loop, must stop/restart recognition around TTS playback, not modify mic constraints.
- **DEEP-OS learning pipeline architecture**: `backend/memory/brain.py` is the canonical neuron extraction module (imported by loop.py). `backend/agents/brain_learner.py` was orphaned — now a backward-compat wrapper. `backend/core/rag.py` rebuilds FAISS vectorstore using HuggingFace `paraphrase-multilingual-MiniLM-L12-v2` embeddings via langchain_community. If langchain not installed, `rebuild_vectorstore()` fails silently.
- **Orchestrator not wired to main chat (2026-07-10)**: `classify_task()` in `orchestrator.py` only runs in `/agent/execute` endpoint (agent.py:20-21). The main `/chat/stream` in `chat.py` does NOT use the orchestrator — it uses mood/personality system. The "Roteamento inteligente de tarefas" shown in Agentes tab is UI-only; it doesn't affect normal chat behavior.
- **Frontend correctly sends workspace root (2026-07-10)**: `App.tsx` line 740 sends `root: expRoot` in chat body. Backend `chat.py` `execute_tool_fn` correctly injects `msg.root` into tool params (lines 853-859). The workspace root IS being propagated.
- **Team system is minimal (2026-07-10)**: `team.py` is just an in-memory message queue with no actual agent execution. The `send_message` and `get_messages` functions are not integrated into the main agent loop. May need enhancement for multi-agent coordination.
- **Agent orchestration tab is UI-only (2026-07-10, CONFIRMED)**: "Agentes" tab shows 5 roles: Jarvis, Architect, Debugger, Planner, Coder. "Roteamento inteligente de tarefas" is claimed but `classify_task()` in `orchestrator.py` only runs in `/agent/execute` endpoint (agent.py:20-21). The main `/chat/stream` endpoint does NOT use the orchestrator — it uses mood/personality system. The routing has no effect on normal chat interactions.
- **Agent routing configuration now exists (2026-07-10, IMPLEMENTED)**: `AgentRoutingConfig` in `agent_config.py` stores per-agent provider/model/temperature/enabled. API at `/api/config/agent-routing`. UI in `AgentsPage.tsx`. Config in `config.yaml` under `agent_routing`. Affects `/agent/execute` only; main chat still uses mood/personality. Future work: wire routing to main chat flow.
- **execute_python workdir injection (2026-07-10, FIXED)**: `tool_execute_python()` accepts `workdir` param, changes `os.chdir()` before execution. `execute_tool_fn` in chat.py injects `msg.root` as workdir. Without this, Python code runs in backend directory and relative paths like `src/app/dashboard` don't exist.
- **Workspace path validation blocks cross-drive access (2026-07-10, FIXED)**: `resolve_path()` in `backend/tools/explorer.py` had `str(target).startswith(str(base))` check that prevented cross-drive access. Fix: Modified to handle absolute paths directly without validation. Sandbox blocking in `system_tools.py` also removed. Agent can now work on external projects on different drives.
