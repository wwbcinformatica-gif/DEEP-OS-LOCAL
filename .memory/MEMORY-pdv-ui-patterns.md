## WBC-ZERO-G 5.0 platform references
- Frontend: React + TypeScript + Vite at `frontend/`
- Backend: FastAPI + Python + httpx at `backend/`
- **Cloud tool calling blacklist**: `CLOUD_NO_TOOL_MODELS` in `chat.py` filters models that don't support tools (deepseek-v4-flash, gemini-flash, mixtral-8x7b, nemotron, etc.). Old `NO_TOOL_MODELS` only covered Ollama vision models. Keep both sets in sync when adding new models to `MODELS` in constants.ts.
- Non-Ollama providers pass `api_key` through the Message model to `stream_chat_with_tools()` and `stream_chat()`
- Core LLM logic lives in `backend/core/llm_native.py` (stream_chat, stream_chat_with_tools, complete_chat)
- 26 route files in `backend/routes/`; chat routing in `chat.py`
- `stream_chat_with_tools()` has fallback: retries without tools on 400/422 errors
- Default mood `opencode` routes ALL messages through `handle_task_stream()` (tool-calling path)

## PDV UI patterns (completed)
- **React multi-tab CRUD forms don't need client-side disabled-save-button**: VendasAvancadas, EstoqueAvancado, Segmentos, CadastrosAuxiliares, Financeiro, FiscalTabelas use backend validation. Only simple cadastro forms (Clientes, ProdutoForm) with explicit required fields benefit. ProdutoForm checks name + price > 0; Clientes checks name + celular.
- **Client required fields are Nome + Celular**: User specified these two as mandatory in client creation (all others optional). Backend validates both in `criar_cliente()`.
- **O.S. default tab is Serviço**: User prefers Serviço (form) as the first tab, Listagem (table) second.
- **Novo Cliente in O.S. context**: Lightweight inline modal next to "Alterar" button in client card. Saves via POST `/api/clientes/` and auto-fills client data into the service form.
- **Model sync**: Both SettingsPage and ChatPanel receive `model`/`setModel` via props from App.tsx (shared state). Both now have identical model list resolution logic — each prepends `{value: model, label: model}` if current model isn't in loadedModels. Provider dropdowns also share `prov`/`setProv`. Model changes in either panel are already bidirectionally synced. If user reports discrepancy, check browser dev tools for runtime state.
- **Action card JSON format**: Backend sends structured JSON with `type: "action_card"`, `title`, `message`, and `buttons[]` (each with `id`, `label`, `action`). Frontend currently renders this as raw text — needs parsing and card rendering in ChatPanel.tsx.
- **Tool confirmation system**: Risk-based via `assess_tool_risk()` in `chat.py` (replaced static `DESTRUCTIVE_TOOLS`). Checks path contents (node_modules, .git, system dirs) and bash command patterns (rm -rf, format, shutdown, etc.). Only `high` and `critical` risk levels trigger confirmation. Flow: backend saves task state → yields `tool_confirm` event (with `risk_level`) → yields `done` with `pending_confirm` → stops stream → frontend shows buttons (critical=red background, high=accent) → user sends `/approve-tool` or `/reject-tool` → backend loads state and resumes. Rejection injects system message telling model to skip.
- **Inline confirmation pattern**: Confirmation buttons render INSIDE the chat input area (above textarea), following the existing `pendingPlan` pattern. Risk-based: critical shows 🔴 "RISCO CRITICO" with red background; high shows ⚠️ "Confirmacao" with accent background.
- **Slash commands**: Intercepted at endpoint level in `chat.py` before normal routing. `/goal`, `/run`, `/clear`, `/help`, `/status`, `/stop` are handled by `handle_slash_command()`. Commands parsed by `parse_slash_command()` which validates against known command set. `/run` reuses `execute_tool("bash")` directly.
- **@ mention system**: `parse_at_mentions()` extracts `@agent` and `@skill` tags via regex. `inject_mention_context()` appends agent personality and skill instructions to `msg.system_prompt`. Known agents: coder, writer, helper, planner, reviewer, debugger, architect, analyst. Known skills: web_search, file_picker, terminal_run, code_review, test_runner, doc_generator, refactor, deploy, memory, brain, plan, explore.
- **Popover UX pattern**: `data-popover` attribute + `mousedown` listener for click-outside detection. Lightweight alternative to portals. Three menus: @ mention (sections: AGENTES + SKILLS), / command, + quick actions with filter input.
- **MIMO API integration**: Model name is `mimo-v2.5` (lowercase). Base URL: `https://api.xiaomimimo.com/v1`. Uses OpenAI-compatible client (AsyncOpenAI). API key flows: frontend `mimoApiKey` state → `api_key` body param → `llm_native.py get_client("mimo")` → `AsyncOpenAI(api_key=key)`. Supports `extra_body={"thinking": {"type": "disabled"}}` and multimodal inputs (image, audio, video).
- **Stock restoration on sale cancel/estorno**: Backend `orcamentos.py` DELETE and ESTORNAR endpoints now restore stock by querying `DAV_ITENS` and running `UPDATE PRODUTOS SET ESTOQUE = COALESCE(ESTOQUE, 0) + ? WHERE ID_PRODUTO = ?` per item. Must use `COALESCE` (Firebird NULL).
- **PDV post-sale auto-reset**: When PrintPreview closes after a sale, `novaVenda()` is called automatically — no manual "Nova Venda" click. Implemented via `onClose={() => { setShowPrintPreview(false); novaVenda() }}` in Pdv.jsx.
- **PrintPreview format toggle**: Managed locally with `formatoLocal` state synced to `formatoProp` via useEffect. Toggle buttons in toolbar. Zoom auto-adjusts (50% for A4, 100% for Cupom).
- **Stock display in PDV**: Search results show `Est: X` with green (>0) / red (0) indicator. Cart table has "Est." column, red text if `quantidade > estoque`.
- **Focus pattern for React components**: After async operations (CRUD, navigation), use `useRef` + `setTimeout(() => ref.current?.focus(), 100)` for reliable focus restore. Immediate focus calls fail due to re-render timing.
- **Orçamento situação/obs save bug (2026-06-22, PARTIAL FIX)**: User reports saving situação/obs in orçamento doesn't persist. Root cause: `database.py` `query_one`/`query_all` lowercase all column names via `d[0].lower()`, so Firebird `LEMBRETE` → `lembrete` in Python dicts. Frontend `Orcamento.jsx:285` used `detalhe.cabecalho?.obs` (undefined → `''`). Fixed line 285 to `detalhe.cabecalho?.lembrete`. Still needs: fix obs display block (lines 290-293), add `carregar()` after save to refresh list.

- **O.S. status colors**: Each of 7 statuses has a unique color — Aberto (yellow #EAB308), Em Analise (blue #3B82F6), Em Andamento (orange #F97316), Aguardando Peca (cyan #06B6D4), Pronto (purple #A855F7), Entregue (green #22C55E), Cancelado (gray #6B7280).
- **Inline panel CRUD pattern (Orçamento/O.S.)**: Single-click selects row → `selecionado` state → `useEffect` fetches detail → `detalhe` state → conditional Card renders below the table. Escape deselects. User expects this same pattern in all list views (Caixa, Vendas, etc.) — NOT modals.
- **Caixa CRUD backend**: `GET/PUT/DELETE /api/caixa/movimentos/{id}`. GET returns movimento + vendas/suprimentos/sangrias. PUT updates totals and auto-recalculates TOTAL_FINAL. DELETE blocks open movimentos and movimentos with linked sales.
- **Caixa status colors**: Aberto = yellow (#EAB308), Fechado = green (#22C55E). Traffic-light: green=done, yellow=active.
- **Dashboard KPI card pattern**: `kpiSelecionado` state + `KPI_FETCHERS` map + `KpiResumo` component. Cards are clickable toggles that filter data. Same pattern to replicate for Clientes/Produtos/Orcamento/Vendas.
- **Backend STATUS_VENDA sync**: When `situacao` changes in orçamento PUT, `STATUS_VENDA` must also be updated (A→A, F→F, C→C). Otherwise the Status badge in the table won't reflect the change.
- **Vendas.jsx periodo wired (FIXED)**: Period filter buttons now send `periodo` param to API. Backend `listar_orcamentos()` converts to `DATA_VENDA >= ?` SQL filter.
